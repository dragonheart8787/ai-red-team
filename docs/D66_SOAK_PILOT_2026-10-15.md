# D66 soak: the harness, three pilots, and why there is no four-hour result yet (2026-10-15)

**Short version.** The soak harness (`scripts/soak/`, method in `docs/D66_SOAK.md`) is built and works: three pilots of 5 to 16 minutes ran the
scheduler, the reconciler and a control plane that never stops proposing, applied five of the six faults (the sixth, a Docker restart, was reached
in pilot 2 and not in the later ones), and checked the invariants. **The four-hour run has not been made.** The pilots found two defects in the
product, and the task's rule is that a finding stops the run and is reported, not fixed and not routed around. One of them (below, F1) would stop
every long run within minutes; so there is no table of four-hour recovery times to give, and none is made up here.

## F1 -- the reconciler stops with "Docker unreachable" when a container is removed while it is listing

**What was seen.** Pilot 3, 08:44:42: `scripts/run_reconciler.py` stopped with exit 5 (`docker_lost`), 31 s after it was started, with no fault
in force; the daemon's own log shows no restart, and a container was destroyed at 08:44:41.

**Why [D, and then E].** `observe.list_containers` calls `client.containers.list(all=True, filters=...)`; the Docker SDK lists the ids and then
inspects each one, so a container that is removed between the two raises `docker.errors.NotFound`. `service._translate` maps any
`DockerException` to `StopService(docker_lost)`, exit 5. `NotFound` is a `DockerException`. **Experiment**
(`python -m scripts.soak.experiment_list_race`, one minute, one container created, started and removed about 2.3 times a second, the reconciler's
own listing in a loop): **109 of 1,554 listings raised `NotFound`**, and the first, run through the reconciler's own `_translate`, gave
`('docker_lost', 5)`.

**What it means.** A listing that races with any dispatch's end stops the reconciler as if Docker had gone away. The documentation says a service
that exits with 5 should not be restarted blindly; here the cause is a healthy daemon and a normal event. In the soak's workload (a container every
few seconds) the reconciler would stop within minutes, every time; in a deployment with a scheduler dispatching one run at a time the window is
small and the odds low and not zero. Nothing is lost or wrong in state: it is a spurious stop. **Not fixed**, by the task's rule. (The same pattern is in
`list_networks`: `network.reload()` and the per-network `containers.list`.)

## F2 -- two dispatches for one allowlist can race on creating the network; one run is refused

**What was seen.** Pilot 1: two runs of one engagement, started together, were refused before they began, `network_unavailable`, with
`could not create the confined network for ('10.66.11.0/24',): 409 Client Error ... Conflict ("network with name cyberorch-allow-2f0c8d15174d already
exists")`. The proposals closed (`network_unavailable`), nothing ran, no state is wrong.

**Why [R].** `DockerSandbox` ensures the network with `networks.get(name)` and, on `NotFound`, `networks.create(name=...)` (`tool_gateway/sandbox.py`,
lines 549-553), with no handling of the 409 a concurrent creator causes; the docstring says "idempotent, because several runs share one allowlist". The
scheduler is serial (concurrency 1, D58-13), so only a control plane that dispatches in parallel meets it — which the soak's worker does, four threads.
**Not fixed.** It is not an invariant of the soak and did not stop pilots 2 and 3 (two refused runs in 150); it is reported because it was found.

## Harness defects found by the pilots (all corrected before pilot 3, none by relaxing a check)

* the audit pairing ignored refused runs (pilot 1);
* a fault was registered after it was applied, not when it began (pilot 2);
* the workload repeated one request per host and was mostly `dedup_hit` (pilot 2);
* the first version of the worker named no network allowlist for its ALLOW requests, and the sandbox then derives the target's own `/32`, which holds no
  container (found with the first drill of item 3 for the same reason);
* `pause_container` waited two minutes for a running container and found none in a quiet moment; it waits five.

Also stated: in the 5-minute pilots the "residue does not grow" check saw its three windows rise while the exited containers were still inside their
5-minute retention; the real run uses 15-minute windows and the same 5-minute retention, and the report prints the floors per window.

## After F1 and F2 were fixed: pilot 4, the diagnostic run, and F3 (2026-10-15, afternoon)

Pilot 4 (14 min, all six kinds drawn) and a diagnostic run that injects only `docker_restart` (the one kind the earlier pilots had not
carried through) with a scheduler wrapper that prints the traceback of whatever ends it as `unexpected_error`. Together: `pause_container` 54.5 s,

at 18.6, 20.5, 20.6 and 20.6 s** (both services stop themselves with exit 5, "Docker lost", and are started again: F1's rule working on a real
restart). 48 invariant checks, none failed; state/audit pairs 222/222, 194/194, 190/190 ... and 243/243, 203/203, 195/195 ...

**F3 (ACCEPTANCE 5.109).** Twice in six daemon restarts (pilot 4; the diagnostic run) the *scheduler* stopped with exit 1, not 5, and the soak
stopped on it by its own rule ("a restart of `dockerd` explains exit 5"). The traceback is in `f3-scheduler-traceback.txt`: the daemon died under a
dispatch in flight, `sandbox.run` raised `requests.exceptions.ConnectionError` after the container had started, the exception went up through
`dispatch_approved` to `Scheduler.tick`, and `scheduler._translate` -- which maps a database loss and an audit failure and nothing else --
made it `unexpected_error`. The documented code for an unreachable Docker is 5. Not fixed; the rule of the soak is not widened.
A four-hour run would meet it at the first restart that catches a dispatch (about one in three).
